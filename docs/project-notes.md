## 项目概况

`CodaPace` —— macOS 菜单栏应用，监控中转站与订阅制 API 的额度。

核心概念是 **pace = 剩余额度% − 剩余时间%**：不只报「用了多少」，而是回答「按这个速度撑不撑得到下次重置」。

```
Sources/Core/     纯逻辑，SwiftPM 暴露，全部可单测
Sources/App/      SwiftUI 视图、菜单栏绘制、偏好、通知、钥匙串
Tests/CoreTests/  自建的极简测试框架（CLT 无 XCTest），用例需在 TestRegistry.swift 显式登记
docs/             本文件、决策、坑、记录 + 两份 backlog
Scripts/          图标生成器，平时不用动
```

面向用户的说明在 `README.md` / `README.zh-CN.md`；本文件讲的是「怎么接着改」。

## 1. 架构

### 1.1 不变量的来由

规则本身在 AGENTS.md「必须遵守的不变量」，编号与这里一致。

这些是跨条目建立起来的，违反会把已修的缺陷重新引入。**代码注释里直接按编号引用它们。**

#### 1. 三种账户键口径，各有其因

| 键 | 组成 | 用途 | 为什么不同 |
|---|---|---|---|
| `storageKey` | providerID + apiId | 历史分区 | 中继换网址还是同一份用量，但换一家供应商就是另一回事 |
| `preferenceKey` | baseURL + apiId | 偏好分区 | 「日重置在几点」是那个部署的配置 |
| `notificationNamespace` | providerID + baseURL + apiId | 通知去重 | 无迁移成本，可用最严口径 |

`storageKey` 里的 `providerID` 是 EXT-009 加的，起因是一个**真实的碰撞**：tu-zi 的账户标识是响应里的 `key_id`（一个短整数），而自建中转站的 apiId 可以是任意字符串；撞上则两个账户的历史静默合并，且合了分不开。老用户的历史靠 `legacyStorageKey` 惰性认领接上 —— 哈希单向，库自己算不出映射，只有「用户切到哪个账户」那一刻才同时知道两个键。**只有兜底适配器的账户能认领老分区**，别家去认领会正好认到另一家的历史。

`preferenceKey` **仍然不含 `providerID`，而且不需要含**：它已带 baseURL，两家的服务地址不可能相同。键加得越多能撞上的越少，而每加一个都要付一次迁移的代价 —— 只在真会撞的地方加。

#### 2. 跨 `await` 必须校验身份

刷新、测试连接、通知投递都是同一套：**开头把身份定住 → 提交前比对 → 不符就整份丢弃**（不显示、不入库、不通知）。共用实现是 `InFlightGate<Token>`。

绝不要在流程中途回头读全局配置 —— OPT-001 就是这么串账户的。

#### 3. 不发明数据（本项目最核心的立场）

「未知」「零」「不限」是三件事，压成一个值就是撒谎。已体现在：

- `QuotaReading.limit: Double?` —— 有上限 / 当时不限(0) / 不知道(nil)。**按桶各自可选**，一个桶的上限未知不牵连别的（阶段 2 前是四列一起判，任一为 NULL 整组算未知）
- `UserStats.hasCompleteUsage` —— 响应缺字段就不入历史
- `TokenAttribution.unattributed` —— 归不到某天就如实记成未归属，**不丢也不硬塞**
- `QuotaConnector.isBoundaryInferred` —— 推算的边界不能画成已知事件
- `TokenTooltip.requests: Int?` —— 为 0 时分不清真假，不显示
- `PaceVerdict.unavailable` —— 没有可信当期窗口就不给判断
- `QuotaUnit.unknown` —— 供应商没说单位就显示裸数字，不默认美元

**遇到缺数据时不要「取个合理默认值」让流程跑通**，那正是本项目反复在修的 bug 形态。缺就如实标缺。

但这条**禁止的是编造，不是禁止采信供应商自己的声明** —— 而「供应商说了」不等于「JSON 字段名里写了」。tu-zi 的单位就是这么定下来的：响应里一个币种标记都没有，但对方自己的用量页面把同一个数字显示成 `$12.50`。采信那个不算发明（详见 §1.2 tu-zi 那段）。判据是**有没有一个可核对的来源**，不是它长在哪个字段上。

#### 4. 日历规则 ≠ 固定时长

夏令时切换日会分道扬镳（「每天 0 点」那天只有 23 小时；「每隔 24 小时」会漂到 1 点）。由 `ResetPolicy` 七种策略分别处理，**不要**再引入「统一按秒数往回推」的算法。

#### 5. 单一路径，不留平行实现

已删除 `AlertPolicy.newAlerts`、`TimeWindow.cycleStart`、`SnapshotBuilder`，因为它们各自与另一处逻辑重复、会随时间漂移。新增功能时优先合并而非并列。

**这条也适用于文档**：一件事只记在一处，别新建 `NOTES.md`、`TODO.md` 之类的平行文件，改就改在原处。2026-10-03 起文档按 code profile 分工（D-1）：逐条缘由在 backlog，跨条目决策在 decisions，坑在 pitfalls，历史在 log，这是规定的分工，不算平行文件。

#### 6. 供应商细节只许待在适配器里

通用层（`UsageService` / `Config` / 历史 / 通知）不该出现 `apiStats`、`admin-next`、`UserStats` 这类字样，也不该认识任何一条具体额度的名字。核查命令见 AGENTS.md 不变量 6，无输出即通过。命中 `RelayProvider.swift` / `RelayModels.swift` 不算泄漏 —— 那是那一家的地盘。EXT-009 已把 DTO 从原先那个名字很通用的 `Models.swift` 拆开：通用的严格解码机制留在 `Decoding.swift`，中转站的线上格式挪进 `RelayModels.swift`，tu-zi 的在 `TuziProvider.swift` 里。

这条最近一次被违反是在菜单栏自动选择里：原先写死「排除叫 `window` 的那条额度」，那是中转站的额度名漏进了通用层。已改为按**周期长度**判定（EXT-001）。

### 1.2 EXT-001 动态额度桶与适配器

分四个阶段，每阶段自己能编译、能跑、能提交（**四个阶段全部完成并已提交**）：

| 阶段 | 内容 | 状态 |
|---|---|---|
| 0 | 钥匙串可行性 | **完成**（见 §2「钥匙串可用」） |
| 1 | 额度桶进显示路径（`QuotaKind` → `QuotaBucket`） | **完成** |
| 2 | 历史表改高表（v3 → v4） | **完成** |
| 3 | tu-zi 适配器 | **完成** |

阶段 1 那三处 `⚠︎` 临时桥接**已全部删除**，`QuotaKind` / `QuotaLimits` / `Sample.cost(for:)` 连同消失。现在历史层存的是 `Sample.quotas: [String: QuotaReading]`，适配器报几条额度就存几条。

一个贯穿的支点：**中转站的四个桶 ID 取值刻意等于旧 `QuotaKind` 的 rawValue**（`total` / `daily` / `weeklyOpus` / `window`）。同一个字符串活在三处存量数据里 —— 菜单栏固定选择的偏好、通知去重键、以及 v3 → v4 迁移时从四个固定列摊出来的桶行。改了它，老用户的菜单栏选择会失效、当前周期已发过的告警会重发一遍、历史曲线会对不上。**不要改**（`testUpgradingFromV3ExpandsTheFixedColumnsIntoBuckets` 会当场变红）。

#### 现在有两个适配器

（2026-09-29 起是四个：又接了 sub2api 和 claude-code-hub 两个中转站软件，见 EXT-011 条目末尾。下表只比较最初这两个。）

| | 中转站 | tu-zi |
|---|---|---|
| 用户输入 | 用量页面网址 | 一把 `sk-` key |
| 认证 | 查询参数里的 apiId | `Authorization: Bearer` |
| 信封 | `{success, data}` | `{code, message, data}` |
| 额度 | total / daily / weeklyOpus / window | daily / weekly / monthly |
| 单位 | 美元（字段名就是 cost） | 美元（**证据在用量页面，不在 JSON**，见下） |
| 重置时刻 | 要靠观测学习 | 服务端每次都给 |
| 账户身份 | 网址里的 apiId | **响应里的 `key_id`** |
| 凭据存储 | UserDefaults 明文 | **钥匙串** |

几乎没有一处相同，而通用层为此**没有长出一个 `if`** —— 那正是 EXT-002 的验收标准。

两条因此立下的规矩：

- **身份在响应里的适配器必须先「测试连接」才能保存**（`accountIDComesFromResponse`）。没跑过就没有身份，编一个会在真身份到手那天把历史和偏好劈成两半。界面上保存按钮会灰着，并说明为什么。
- **安全说明跟着 `credentialSensitivity` 走**。从前设置窗口写死一句「apiId 只能查看用量，不能发起请求」—— 那是中转站的性质被当成了通用前提。对一把能花钱的 key 照搬那句，是个假的安全承诺。

**tu-zi 的单位：证据来自供应商自己的用量页面，不是 JSON。**

响应里 `daily_used` 这类字段一个币种标记都没带，整份 JSON 只有 `fuel_pack.available_usd` 写了 `_usd`。所以最初声明的是 `.unknown`（显示裸数字）—— 只看 API 能得出的结论只有这一个。

2026-09-24 用户核对了供应商的用量页面：**同一个数字**在那里显示为 `$12.50 / $30.00`。据此改成 `.money(currency: "USD")`（当时还声明了 `.costAmounts`，这项声明 2026-10-05 删了，见 D-2）。

这不违反「不发明数据」—— 那条禁止的是编造，不是禁止采信供应商自己的声明；对方只是把单位说在了另一个渠道。**要紧的是：只看那份 JSON 会觉得这里写错了。** 代码注释和测试 `testAmountsAreUSDPerTheProvidersOwnUsagePage` 里都钉了证据来源，要翻回 `.unknown` 得先拿出新证据（比如页面改成了别的币种），而不是因为「JSON 里没写」。

#### 阶段 2 / 3 留下的三件事

- **`samples` 表的四个额度列没删**，新行一律写 0 占位，**任何代码都不再读它们**。留着是为了万一要退回 v4 之前的版本，那之前的历史还在原处。SQLite 的 `DROP COLUMN` 支持看版本，删了反而不好回头。
- **`Sample.allTokens` / `requests` 仍是非可选的**。不报累计值的供应商（tu-zi 一个都不报）在库里留下的是 0 而不是「未知」。眼下骗不到人：相邻两条都是 0，`TokenDelta` 返回 nil，一条 token 记录都不写，面板那行也整行不显示。但要加「累计 token 趋势」之前，得先把这两列也改成可选。
- **`Snapshot.totalCost` 没有任何读者**，纯写入。删一个 public 字段是另一个决定，没顺手做。

### 1.3 EXT-010 账户存档与快速切换

用户 2026-09-24 提出，**同日完成并实机验证**。改法、取舍和刻意未做的部分在 `provider-and-chart-backlog.zh-CN.md` 的 EXT-010 条目末尾「修复记录」。

几处接着改时容易踩的：

- **切换不复用 `Config.apply`**。`apply` 要写钥匙串所以必须有密钥；切换走 `Config.select`，只写身份。两者之后的清场共用 `UsageService.accountDidSwitch` —— 换账户要多做一件事，改那一处。
- **存档列表只有一个写入方**：`UsageService` 的三个函数。别从 Config 那边直接改 `Config.archive`，界面上的 `@Published` 副本会和存储漂开。
- **当前账户不许删**，删除 = 删列表项 + 删钥匙串，历史库留着。
- 切换最终放在**设置窗口的存档列表**里，面板头部只显示账户名。面板上曾做过一个下拉，用户看过实机后去掉 —— 别再加回去，除非用户改主意。

一句话概括为什么它比听起来小：历史、钥匙串、学到的日重置、通知去重**已经全都按账户分区**，切走再切回来一样不丢。整个应用里唯一单值的只有「此刻选中的是哪个」。

### 1.4 换账户的代价，以及「账户存档」会放大它

换账户时 `HistoryRecorder.accountDidChange()` 会丢掉 token 增量基线，跨过那次切换的用量归属会打折扣。今天这不构成问题，**原因只是切换很麻烦**：要去对应网站翻出 apiId 或 API Key 重新粘一遍，没人一天切五六次。

用户提出要做「账户存档」（配置成功后存下来，下次从下拉里直接选，可自定义名称）—— 那个功能的全部意义就是把切换变廉价。**切换一廉价，这个缺陷就会被放大**：一天切五六次，就有五六段用量归属不准。

记在这里是因为两件事在代码里隔得很远：基线在 `HistoryRecorder`，而下拉会长在面板上。做存档功能之前先决定这个怎么办，别等用户发现某天的 token 柱子矮了一截才回头找。

**已解决（2026-09-24）：** 基线本身没问题（切回来从库里补，等价于重启，总量不丢），折扣其实来自归属策略里一条「间隔超过 30 分钟就不归当天」的规则，已撤掉。现在当天切走再切回，用量完整记在当天；只有跨午夜才进未归属。详见 EXT-010 条目。

（相关：历史、钥匙串、学到的日重置、通知去重**已经全都按账户分区**，切走再切回来一样不丢。唯一单值的只有「此刻选中的是哪个」——所以存档功能比它听起来小得多。）

### 1.5 已知的用户可见影响

OPT-008 之后，升级的老用户会看到**额度曲线的历史段消失**（那些采样没记过当时的上限），随新采样积累在 7/14/30 天窗口内自行恢复。这是有意的：替代方案是拿当前上限重写过去，正是该条要修的 bug。OPT-012 已让界面如实说明有多少条采样画不出来。

### 钥匙串可用（2026-09-22 实测）

ad-hoc 签名、没有 provisioning profile 的 app **能用钥匙串**，写、读、删三步都实机验证过（`Sources/App/KeychainStore.swift`）。

前提是走**文件版**钥匙串——即**不要**设 `kSecUseDataProtectionKeychain`。数据保护版要求 `keychain-access-groups` 权限，而那随 provisioning profile 分发，本项目没有。首次访问时系统会弹一次授权框，这是文件版的正常行为，不是故障。

`import Security` 由 swiftc 自动链接，`build.sh` **不需要**补 `-framework Security`（已验证）。

这条要紧，是因为它是 EXT-001 唯一能否决整条计划的未知：`.secret` 级凭据没地方存的话，需要 API Key 的供应商一家都接不了。

## 6. 开发规划

### 6.1 应用内更新：已做「只提醒」，一键安装未做（2026-09-26）

**已实现并实机验证（2026-09-26）：只提醒，不安装。** 面板最下方（滚动区和底栏之间、固定不滚）在有新版时出现「有新版本 X ›」，点了打开 `releases/latest` 页面，用户自己下载或跑 README 的命令行重装。

- `Sources/Core/ReleaseVersion.swift`：去掉前缀 v、逐段按整数比（`2.10 > 2.9`、`2.0 == 2.0.0`），解析不了返回 nil、不提醒。5 例测试，反向验证两处（按字符串比、不补零）。
- `Sources/App/UpdateChecker.swift`：启动查一次、之后每 24 小时一次，请求 `api.github.com/.../releases/latest`（自动跳过草稿和预发布）。**失败不显示不报错**，保留上次结论。
- 用户定的：点击打开 Release 页面而非仓库首页；默认开、**不加开关**；README 隐私说明已写明每天访问一次 `api.github.com`。
- README 的命令行升级改为「先退出、`rm -rf` 旧 app，再跑三条安装命令」—— `ditto` 是合并进已有 app 而不是替换，不删会留下旧版文件。**已发布的 v2.0 Release 说明里仍是旧写法**，没去改线上内容。
- 实机测法：`./build.sh` 后用 PlistBuddy 只把 `build/` 里那份的版本改低（如 1.9）再 `codesign --force --sign -`，仓库的 `Info.plist` 不动。

**新版能「无感接上」的前提，以后每一版都得守**：用户数据全在 app 包外（偏好 plist、`History.sqlite`、钥匙串），所以 **bundle ID `com.hesher.codapace`、偏好键名、钥匙串服务名 `CodaPace` 永远不改，数据库迁移只向前**。任何一个改了，替换 app 就会丢数据。唯一的不无感：ad-hoc 签名下每把 tu-zi key 会再弹一次钥匙串授权框。

以下是「一键下载安装」的讨论，**没做**，留作参考。要做时这些仍然成立。

用户最初提出：一是发新版时提醒用户，二是点一下就下载安装。第二件的四个待决问题用户暂不回答，后来选了只做提醒。

**不用 Sparkle，自己做。** Sparkle 是 macOS 上的标准方案，但它违反零第三方依赖的约定（见 AGENTS.md「代码风格」），要以 framework 嵌进 app、维护 appcast，没有 Xcode 构建更麻烦。而需要的功能用系统框架就够。

**方案三块：**

1. **检查**：请求 `api.github.com/repos/rigelmansid/CodaPace/releases/latest`，把 `tag_name`（`v2.1`）和 `CFBundleShortVersionString` 按数字逐段比较。启动时查一次，之后每 24 小时一次（GitHub 未登录限额每小时 60 次，够用）。有新版时面板最下方出现一行「有新版本 2.1 · 更新」，没有时不占位置。
2. **安装**：下载 `CodaPace-arm64.zip`（发版时附件名固定，`releases/latest/download/…` 这条路现在就通）。app 自己用 `URLSession` 下载的文件不带隔离标记，和命令行安装一样不会被 macOS 拦。解压到临时目录、校验通过后，交给一段 shell 脚本：等 CodaPace 退出 → `ditto` 覆盖到当前 app 所在位置 → `open` 重启。**所在目录没有写权限时退回打开 Release 页面**，不申请管理员权限。
3. **更新之后**：tu-zi 的 key 每条会再弹一次钥匙串授权框（ad-hoc 签名换了程序身份，见坑 2）。更新提示里可顺带说一句。

**安全：一键安装最要紧的一点。** 「从网上下载代码并替换自己」是整件事的最大风险：

- 只靠 HTTPS 不够 —— GitHub 账号被盗，攻击者发一个 Release，所有人点更新就装上了。
- Release 说明里放 SHA-256 没用 —— 哈希和包出自同一处，能改一个就能改另一个，只防下载损坏，不防篡改。
- codesign 校验没用 —— ad-hoc 签名只证明完整，不证明是谁签的。

**建议的做法：CryptoKit 的 `Curve25519.Signing`**（系统框架，零依赖，Sparkle 用的也是 EdDSA 这个思路）。本地生成一对密钥，**私钥只留在用户自己机器上**，公钥编进 app；每次发版用私钥给 zip 签名，签名文件作为 Release 的第二个附件；app 下载后先验签，对不上就拒装。这样 GitHub 账号被盗也发不出能通过验证的更新。

代价：发版流程多一步签名；**私钥丢了，已装的旧版本再也收不到自动更新**，只能让用户手动下载一次。

#### 签名校验细节（2026-09-25 续议，仍未决定）

**它防什么、不防什么。** 本质是把信任从「GitHub 账号」挪到「一把私钥」，安全程度等于私钥的保管程度。

| 攻击 | 防得住吗 |
|---|---|
| GitHub 账号被盗，发了恶意 Release | 能 —— 没私钥签不出有效签名 |
| 下载途中被改（中间人、CDN） | 能 |
| 把**旧的、签过名的**版本重新发成 latest（降级攻击） | **只签 zip 防不住**，见下「签什么」 |
| 开发者自己的电脑被入侵，私钥和 GitHub 一起丢 | 不能 —— 两道锁都丢了 |
| 开发者自己发了有问题的代码 | 不能 —— 签名只证明「是谁发的」，不证明「发的东西没问题」 |
| **首次安装** | **不能**，见下「首次安装」 |

**为什么攻击者能换 zip、却换不了签名。** 签名文件他当然能换，但换上去的签名无效。私钥**生成**签名，只在开发者机器上；公钥**验证**签名，编在用户**已装好**的 app 里、不在 GitHub 上。攻击者用自己的私钥签，对不上用户手里的公钥；编一串字节，也对不上；用开发者的私钥签，他拿不到。换文件容易，造出能被那把公钥验过的签名在数学上做不到。

和 SHA-256 的区别就在这：哈希不需要任何秘密，谁都能算，换了包顺手重算一个填上就对上了；签名需要私钥才造得出。类比：哈希是包裹上写「内有 3 件」，谁都能改写；签名是只有你有的印章盖的火漆，别人能撬掉、盖不出。

公钥也换不掉：它在用户本地的 app 里，要换只能让用户装一个带新公钥的新版本，而新版本得先过旧公钥的验证 —— 死循环，对攻击者不利。**这把锁对开发者自己同样生效**，所以私钥丢了旧 app 就收不到自动更新。

**首次安装是真正的薄弱点。** 整套逻辑的前提是用户手里那个 app 可信。第一次安装时还没有 app 在验证：攻击者若在用户首次下载前就控制了 GitHub，可以直接发一个编进**他自己公钥**的恶意 app，此后这个用户收到的「更新」都是攻击者签的、且都验得过。**签名保护的是更新，不保护首次安装。** 首次安装的信任只能靠别的：用户从源码构建；在 GitHub 以外公布公钥指纹供核对；或者 Developer ID + 公证由 Apple 把关。

**四个部件：**

1. **密钥对**：Curve25519，私钥 32 字节（base64 约 44 字符，易备份）；公钥 32 字节，作为常量编进 **Core**。
2. **签名脚本** `Scripts/sign-release.swift`（同 `make-icon.swift` 的写法）：读私钥、签名、写出签名文件。
3. **发版流程**：构建 → 打 zip → **跑签名脚本** → 上传 zip **和签名文件**。
4. **app 端验签**：纯逻辑，放 Core 可单测。要测：正确签名通过、zip 改一个字节失败、别的密钥签的失败、签名文件格式坏失败、版本降级被拒。每条照例反向验证。

**签什么：建议签一份小清单，不直接签 zip。** 清单三行：`CodaPace` / 版本号 / zip 的 SHA-256。app 端依次检查：清单签名有效 → 清单版本号**大于**当前版本（防降级）→ 下载的 zip 哈希与清单一致 → 解压后 `Info.plist` 版本与清单一致（多一道保险）。仍只多一个附件，但同时锁住「哪个文件」和「哪个版本」。这里的 SHA-256 有用，因为它被签名罩住了，改不了。

**私钥保管。** 两头风险相反：丢了 → 旧 app 收不到自动更新；泄露 → 还要和 GitHub 被盗叠加才出事。建议：

- 日常放开发者的登录钥匙串，签名脚本用 `security` 命令读 —— 不进仓库、不是散落在硬盘上的文件。
- 那 44 个字符存进密码管理器或抄写离线保存。**备份比日常存放更要紧。**
- 签名脚本拒绝从仓库目录读私钥，`.gitignore` 再加一道。

**丢了或泄露之后。**

- **丢了**：可恢复，但每个用户要手动一次。验签失败时 app 不只报错，而是提示「无法验证更新，请到 Release 页面手动下载」并给按钮；手动装上的新版带着新公钥，自动更新就回来了。
- **泄露了**：立刻用还有效的旧私钥签发一个换了新公钥的版本 —— 和攻击者抢时间，但比没办法强。
- **预置两把公钥（在用 + 备用）不做**：为没发生的事多保管一把钥匙；真要换钥时「旧钥签发新钥」就够。

**另一条路：Apple Developer ID（每年 99 美元）+ 公证。**

| | CryptoKit 自签 | Developer ID |
|---|---|---|
| 费用 | 免费 | 每年 99 美元 |
| 防 GitHub 被盗 | 能 | 能（codesign 校验 Team ID 才有意义） |
| 钥匙串每次更新都弹 | 还弹 | **不弹** —— 程序身份跟着证书，不跟二进制哈希 |
| 浏览器下载首次打开被拦 | 还拦 | 公证后不拦 |
| 首次安装的信任 | 靠不了 | 由 Apple 公证把关 |
| 要写的代码 | 验签逻辑 + 签名脚本 | 基本没有 |
| 无 Xcode 可用吗 | 可 | 可（`codesign`、`notarytool` 都在 CLT 里） |

Developer ID 一次解决三件事：更新安全、钥匙串反复弹、Gatekeeper 拦截（后两件现在都写在 README「已知局限」里）。代价是钱和维护一个开发者账号。
