## 目标与基本原则

1. 支持可用于 Codex、Claude Code 和多个模型的 API 订阅，准确显示其共享额度或独立额度。
2. 用量与消费速度以供应商实际计费、限额的额度桶为核心。用户使用哪个客户端或 agent，不应自动改变额度归属。
3. 供应商明确提供产品级或模型级独立限制时，分别展示；没有依据时不推断、不拆分，也不重复累加共享用量。
4. 支持不同用量链接、后台地址、接口协议、认证方式和重置规则。
5. 保留历史数据的真实性：未知值不当作零，空档不当作连续实测，无法归属的增量不强行分配。
6. 图表增加悬停详情；亮色主题下保持灰白中性色和现有彩色数据元素，避免出现难辨认的黑色区域。
7. 保留 macOS 13 兼容性，现有 claude-relay-service 用户应能平滑迁移。

## 构建环境（2026-09-21 已解决）

一度无法构建 app:CLT 升到 Swift 6.4 后,较新 SDK 的 SwiftUI 把 `@State` 声明成宏,展开需要 `SwiftUIMacros` 插件,而它只随 Xcode.app 分发。于是所有含 `@State` 的文件都编不过,UI 相关条目全部无法验证。

**解法**:`build.sh` 改为显式指定 `MacOSX26.sdk`(该版本的 SwiftUI 还没这么做),CLT 环境重新可以独立构建。产物已验证:arm64、`minos 13.0`(macOS 13 兼容性保持)、ad-hoc 签名。找不到该 SDK 时会打印提示并退回默认。

**代价记录**:在此之前 `SettingsWindow` / `HistoryWindow` / `PopoverView` / `HistoryCharts` 长期只有部分类型检查。解开后第一次全量检查就发现 `PopoverView.reloadHistory` 仍在用 EXT-004 之前的旧签名(`window:` 而非 `rule:`)——改 `HistoryWindow` 时漏了它,而它编不过所以一直没暴露。已修。

## EXT-001：动态额度桶与订阅范围显示

**现状与需求：** 当前额度类型固定，包含“本周 Opus”等特定名称。接入 Codex 专属订阅或多模型共享订阅后，这些名称和固定布局不能完整表达实际限制。

**建议模型：** 将固定额度扩展为 `QuotaBucket`。以下字段表达职责，实际实现可按现有 Swift 代码风格调整。

| 字段 | 含义 |
|---|---|
| `id` | 供应商范围内稳定的额度桶标识，不使用展示名称作为主键 |
| `title` | 供应商映射后的可本地化名称 |
| `scope` | 账户共享、产品专属或模型专属 |
| `products` / `models` | 明确支持的产品或模型，可为多个或未知 |
| `metric` / `unit` | 金额、token 或请求数及其单位；金额应带币种 |
| `used` / `limit` | 实际用量和上限；区分未知、不限与真实零值 |
| `window` / `resetPolicy` | 当前周期和对应重置规则 |
| `provenance` | 时间及额度信息来自服务端、用户配置还是推算 |

**展示规则：**

| 供应商实际限制 | 建议展示 |
|---|---|
| 多个产品、模型共用一个总额度 | `API 共享额度`，副标题列出已知适用范围 |
| 只有 Codex 使用的独立额度 | `Codex 专属额度` |
| 只有 Claude Code 使用的独立额度 | `Claude Code 专属额度` |
| 明确存在 Opus 独立周限制 | `Opus 模型额度`，周期信息显示“本周” |
| 只提供账户统计，不提供产品范围 | `账户额度`，不猜测具体模型或客户端 |

速度计算仍使用“剩余额度比例减去剩余时间比例”，前提是存在有效上限和可信的当前周期。模型范围与重置周期分别表达，避免将“本周 Opus”固化为不可扩展的类型。

同一消费可能同时受共享总额度和模型子额度约束，两者可以同时展示，但不能相加成总消费。菜单栏固定选择改为绑定稳定额度桶 ID；自动选择继续考虑短窗口频繁波动的问题。

**验收标准：** 共享、多产品、Codex 专属、Claude Code 专属、模型子额度等样例均显示正确；切换客户端不导致同一共享额度被拆分或重复计数；未知范围不被误标。

**实施记录（阶段 0–3 全部完成）**

本条分四阶段做，每阶段自己能编译、能跑、能提交。拆分的理由是上一次攒了两周未提交的教训。

- **阶段 0 · 钥匙串可行性**：ad-hoc 签名、无 provisioning profile 的 app 能用文件版钥匙串（见 `KeychainStore.swift` 与项目须知）。这是整条计划唯一能否决后面全部的硬未知，所以先打掉——`.secret` 级凭据没地方存的话，需要 API Key 的供应商一家都接不了。
- **阶段 1 · 额度桶进显示路径**：`Gauge` + `QuotaKind` → `QuotaBucket`，新增 `QuotaUnit`（含 `.unknown`）与 `BucketTitle`（本地化名 / 供应商原名两态）。菜单栏自动选择的判据从「排除叫 `window` 的那条」换成「周期短于 `QuotaThresholds.volatileWindow`」——**额度名是供应商的事，通用层不该认识任何一条具体额度的名字**（不变量 6）。
- **阶段 2 · 历史表改高表**：`samples` 的四个固定额度列 → `quota_samples`（`account_key, ts, bucket_id, used, limit_value`），`user_version` v3 → v4 逐行展开。`Sample` 改为 `{at, allTokens, requests, quotas: [String: QuotaReading]}`；阶段 1 那三处 `⚠︎` 桥接全部删除。
- **阶段 3 · tu-zi 适配器**：`TuziProvider.swift`。新增 `Connection`（身份 + 凭据，一次取齐传进适配器）、`accountIDComesFromResponse`、`ConnectionReport.stableAccountID`、`ProviderRegistry.resolvedForSaving`、`learnableDailyBucketID`。钥匙串经 `Config.apply` / `Config.connection(for:)` 接通——EXT-003 建 `CredentialSensitivity` 时留的那道守卫，在这里第一次被真正走通而不是拦下。

  它和中转站几乎没有一处相同（认证、信封、额度形状、重置来源、身份来源、凭据存储全不同），而通用层**没有长出一个 `if`**——EXT-002 的验收标准到这里才算真被检验过。

**两条因此立下的规矩：**

- **身份在响应里的适配器必须先 verify 才能保存。** tu-zi 的输入是一把 key，里面没有账户标识，只有 `key_id` 是它。退而求其次地编一个（拿 key 的哈希顶上）看着能跑，代价是真身份到手那天分区键会变——等于把历史劈成两半。**不发明数据同样适用于身份。**
- **安全说明必须跟着 `credentialSensitivity` 走。** 设置窗口原先写死一句「网址里的 apiId 只能查看用量，不能发起请求」，那是中转站的性质被当成了通用前提。接入带密钥的供应商后照搬那句，是对着一把能花钱的 key 做假的安全承诺——比不说更糟。

**支点：中转站的四个桶 ID 取值刻意等于旧 `QuotaKind` 的 rawValue**，同时买到三样零迁移——菜单栏偏好、`QuotaAlert.dedupeKey`、以及 v3 → v4 的列到行映射。

**比旧结构更精确的两处**（不是顺手改，是高表天然带来的）：

- 一个桶的上限未知不再牵连另外三个。旧版四列任一为 NULL 就把整组判未知，于是一条上限齐全的额度会因为隔壁那条缺上限而整条画不出来。
- 「这次采样里没有这条额度」（键不存在）和「有，但用量是 0」终于分得开。切周期和画曲线都据此不再把缺数据当成一次归零。

新增测试 58 例（323 → 381 全通过）。**反向验证**共注入 16 处缺陷，每处都由对应用例报红、无一静默通过。

阶段 2 的八处：迁移回填 NULL 上限、迁移桶 ID 拼错、缺桶当 0、缺桶画满格、清理留下孤儿行、`LEFT JOIN` 写成 `INNER`、重写采样不清旧桶、缺前值即开新周期。

阶段 3 的八处：把无单位数字当美元、半份窗口也认、没验证也放行保存、不报的累计值填 0、丢掉微秒的日期解析、月额度重复进 `monthlyCost`、重置改成外推、密钥原样进 `description`。

值得记一笔：注入「丢掉微秒的日期解析」时**塌了三条用例**，说明 tu-zi 那个 `2026-09-21T11:19:02.793995+08:00` 的微秒精度是承重的——`ISO8601DateFormatter` 不带 `.withFractionalSeconds` 会直接返回 nil，而后果不是报错，是那条额度**悄悄失去窗口**：倒计时和速度判断一起消失，界面上看不出任何异常。

**tu-zi 适配器里刻意未做的：**

- **`fuel_pack.available_usd` 不产出额度桶。** 它是**余额**，没有「上限」可言。拿 available 当 limit 会让它永远显示剩余 100%（花掉多少，上限就跟着掉多少）。`active_batches` 在样例里是空数组，非空时可能带着原始额度——没有那份样例就设计不了，照本项目一贯的立场不对着假设做设计。计划原文列了这一项，这是对它的一处偏离。
- **顶层 `quota` / `quota_used` / `rate_limit_*` / `usage_*` 全部忽略。** 它们是 0 且 `window_1d_start` 为 null，配合 `billing_mode: "subscription_first"` 可判断是另一条计费路径未启用——**「不适用」不是「用了 0」**。
- ~~**`costAmounts` 声明为假**，尽管那些数字看着就是钱。除了 `available_usd`，没有一个额度字段带币种标记；声明为真会让界面替对方承认一件它没说过的事。~~ **2026-09-24 推翻**：用户核对了供应商自己的用量页面，**同一个数字**在那里显示为 `$12.50 / $30.00`。单位是对方声明的，只是声明在了另一个渠道 —— 采信它不算发明数据。已改成 `.money(currency: "USD")` + `.costAmounts`，证据来源钉在代码注释和两例测试里（只看 JSON 会觉得那是错的）。因此上面反向验证清单里「把无单位数字当美元」那一处，今天已不再是缺陷。
- **调用日志 / token 明细不碰**（用户已定）。因此 `cumulativeTokens` / `cumulativeRequests` / `usageHistory` 全为假，面板上「累计」那行整行不显示，token 柱状图一直空着。

**阶段 2 刻意未做的：**

- **`samples` 表的四个额度列不删**，新行写 0 占位且不再被任何代码读取。留作退回 v4 之前版本的余地；SQLite 的 `DROP COLUMN` 支持看版本，删了不好回头。

阶段 2 遗留的那处写死 `"daily"` 已在阶段 3 修掉：改由适配器用 `learnableDailyBucketID` 声明是哪条额度，tu-zi 返回 nil 整条跳过。

## EXT-002：供应商适配器与能力声明

**现状与需求：** 当前网络层绑定 claude-relay-service 的两个接口。不同供应商可能有完全不同的路径、认证和响应结构。

**建议接口职责：**

```text
UsageProviderAdapter
- providerID / displayName
- detect(input)
- parseConnection(input)
- fetchUsage(connection)
- managementURL(connection)
- capabilities
```

适配器负责协议、认证、响应映射、管理后台地址、额度名称和重置信息。通用服务负责调度刷新、账户切换、错误状态、历史记录和通知。

适配器按服务协议划分，不按 Codex 或 Claude Code 的名称划分：同一个供应商适配器可以返回多个产品的额度。先将现有实现迁移为第一个适配器，再根据真实接口样例接入新供应商。

能力声明至少区分：金额用量、token 用量、累计计数、当前周期计数、模型明细、历史查询、重置时间等。缺少能力时显示未知或隐藏不适用项，不补造数值。

**接入优先级：**

1. 官方或供应商公开的用量 API。
2. 供应商提供的稳定 JSON 接口。
3. 用户明确配置的已知兼容协议。
4. 只有网页后台的供应商先提供“打开后台”能力，实时统计标为未支持；网页抓取作为后续单独评估项。

**验收标准：** 新供应商无需在通用刷新服务中追加大量条件分支；现有供应商行为保持兼容；不支持的统计能力有明确状态；请求和响应始终绑定同一连接身份。

**实施记录（第一阶段完成：接口 + 现有实现迁移）**

按本条自己的要求「先将现有实现迁移为第一个适配器」执行。**刻意没做**：不加第二个适配器（无真实接口样例，凭假设设计等于押注）、不动存储键（属 EXT-009）、不碰额度模型（EXT-001）、不碰重置策略（EXT-004）。

新增 `Sources/Core/Provider.swift`：

- `ProviderCapabilities`（OptionSet）—— 八项能力。放在 Core 而非 App，是因为 `detect` / `parseConnection` / `managementURL` / `capabilities` 全是纯逻辑，只有 `fetchUsage` 碰网络，这样前四项才能单测（原先 `Config.parse` 在 App 层，一直没有测试）。
- `UsageProviderAdapter` 协议。
- `ProviderRegistry` —— `providerID → 适配器`；`parse(_:)` 里 `detect` 只决定**尝试顺序**而非门槛，免得某个适配器的 detect 保守就把一个其实能用的链接判死。

新增 `Sources/Core/RelayProvider.swift`：原有的两个接口路径、`post`、URL 解析、后台地址、以及**响应映射**全部收进来。其中响应映射（原 `SnapshotBuilder`）是从通用的 `Snapshot.swift` 搬过来的——它接受中转站的线上类型 `UserStats`、认识 `currentTotalCost` 这些字段名，坐在通用层里正是「通用层不该认供应商」的直接违反，而文档明确把「响应映射」列为适配器职责。现已改名为 `RelayProvider.buildSnapshot`，测试套件同步改名 `RelaySnapshotMappingTests`。

能力声明不是摆设，两个「不给」有实际后果：中转站没有 `dailyResetTime`（接口根本没有日重置字段，所以 app 要自己观测并标注「推算」）、没有 `usageHistory`（只报当前值，所以历史只能从装上那天起本地积累）。这两条正对应 README 里已有的两句限制说明。能力声明要是全真，它就等于没声明。

`AccountIdentity` 增加 `providerID`：同一个网址在不同协议下含义完全不同，所以它是身份的一部分——也意味着换供应商后在途的旧响应过不了提交前的身份校验（复用 OPT-001 建好的机制）。但 `storageKey` / `preferenceKey` **刻意不含** providerID：算进去会让现有用户的历史分区键当场变掉，等于把他们攒下的曲线全丢掉；带版本的迁移是 EXT-009 的事，在那之前宁可留一个理论上的碰撞（两个供应商恰好用同一个 apiId 字符串，目前只有一个适配器故不可能发生）。已加测试把这个取舍钉住。

调用侧：`UsageService.refresh()` 只说「给这个账户拉一次用量」，协议细节一概不知；`Config.consoleURL` 改为 `adapter.managementURL(for:)`；`Config.parse` 删除，解析归适配器；`SettingsWindow` 的「测试连接」走**和正式刷新完全相同的入口**——域名或路径像不像都不算数，只有真请求跑通才算确认。存量配置没有 `providerID`，读不到时退回兜底适配器，老用户升级无需重新配置。

覆盖测试：新增 `Tests/CoreTests/ProviderTests.swift` 19 例（总数 178 → 197 全通过）——识别不看域名、端口保留、空/缺 apiId 不解析、首尾空白容错（从浏览器复制常带换行）、后台地址由适配器构造、能力声明的真与假、注册表兜底、providerID 参与身份而不参与分区键。

## EXT-003：配置链接识别与连接验证

保留“粘贴用量页面网址”的入口，增加以下流程：

1. 根据域名、路径或用户选择确定候选适配器；域名本身不能作为支持协议的充分证据。
2. 由适配器解析链接、服务根地址和账户标识，保留协议需要的路径前缀。
3. 使用对应认证方式测试连接，验证关键字段和能力。
4. 显示识别到的供应商、共享或专属额度、统计能力及重置规则。
5. 保存 `providerID + connection`，管理后台链接由适配器构造。

账户身份应同时包含供应商、服务地址和稳定账户标识，用于历史、配置及通知隔离。后台地址与统计 API 地址允许不同，不再硬编码统一路径。

新适配器如果需要 API Key、访问令牌或会话凭据，应区分敏感凭据与只读统计标识，设计对应存储方式；不能直接沿用当前 `apiId` 的明文存储假设。

**验收标准：** 已知链接能够识别并验证；未知链接能选择兼容协议或得到明确的未支持状态；更换输入后旧测试结果不能覆盖新输入的状态；保存配置后旧账户在途请求不会污染新账户。

**实施记录（已完成）**

验收标准里的「更换输入后旧测试结果不能覆盖新输入的状态」**是当前代码的真实缺陷**，不只是待建能力：`test()` 发起 Task 后若用户改了网址，`onChange` 只把状态重置为 idle，在途的旧结果回来照样写进 `result`——界面显示「连接成功」，而那说的是上一个网址。

这是 OPT-001 的同一个病：拿一个不区分对象的量当门。于是把该模式提成 `Sources/Core/InFlightGate.swift`（泛型 `InFlightGate<Token>`），`RefreshGate` 改为委托给它，`SettingsView` 用 `InFlightGate<String>` 记住「在飞的那次测试对应哪一段输入」，提交前 `guard input == probed`。反向验证时 `RefreshGateTests` 与 `InFlightGateTests` **同时**失败，说明确实是委托而非复制了一份。

## EXT-004：重置策略与周期标识

**需求：** 支持自然日凌晨重置、每天购买时刻重置、购买后固定时长重置，以及供应商直接提供的周期。

| 策略 | 表达内容 |
|---|---|
| `serverProvided` | 服务端给出的实际起止时间、下一次重置时间或周期 ID |
| `calendarDaily` | 指定时区、小时和分钟的每日重置 |
| `calendarWeekly` | 指定时区、星期及时间的每周重置 |
| `fixedDuration` | 从锚点开始，每隔固定秒数重置 |
| `subscriptionAnniversary` | 按购买日期及日历单位重复，如每个自然月的购买日 |
| `rollingWindow` | 最近一段时间的滑动统计，无统一归零时刻 |
| `inferred` / `unknown` | 有明确推算依据，或尚不能确定 |

每天当地 14:35 重置，应表示为带时区的日历规则；每隔 24 小时重置，应表示为固定时长。两者在夏令时切换时可能不同，不能混用。日、周、月周期使用日历运算，月份末尾的订阅周年规则以供应商定义为准。

规则优先级为：服务端明确数据、已验证的供应商协议或用户配置、历史推算、未知。推算信息继续标记，保存来源和不确定性；服务端时区不默认等于本机时区。

滑动窗口不能套用固定周期的“距离归零还有多久”和当前 pace 公式。没有足够信息时仅展示用量和限制，速度判断设为不可用。

**验收标准：** 自然日、非整点购买时间、固定 24 小时、日历月、夏令时和时区变化均有用例；周期 ID 稳定；未知周期不产生伪造倒计时；滑动窗口不冒充定时重置。

**实施记录（已完成）**

本条把待优化清单里的 **OPT-010、OPT-011 一并修掉**——两者都是同一个根因的症状：全项目只有一种周期算法。

新增 `Sources/Core/ResetPolicy.swift`。核心区分是**日历规则**与**固定时长**不是一回事：

- 「每天当地 0 点」是日历规则。纽约 2026-03-08 只有 23 小时，但它照样是「一天」，下一次重置仍在当地 0 点。
- 「每隔 24 小时」是固定时长，数的是绝对时间，不受夏令时影响。

旧实现只有后一种算法（`TimeWindow.cycleStart` 拿窗口秒数反复往回减），于是日历周期在切换日整体错位。该方法**已删除**——留着就是留一个会被再次误用的坑。

七种策略全部实现：`serverProvided`（**不往外推**，对方只说了这一段）、`calendarDaily`、`calendarWeekly`、`fixedDuration`、`subscriptionAnniversary`（按自然月，day 夹到月末）、`rollingWindow`（无统一归零时刻 → 算不出周期）、`unknown`。

`ResetProvenance` 五级，顺序即文档写的优先级：`server > configured > observed > inferred > unknown`。其中 `observed` 是为现实补的一级——从历史里真实观测到的归零事件比「先当作本地零点」可信得多，`isCertain` 以它为界，正好对应界面上要不要标「推算」。

`ResetSchedule` 改为产出规则（`dailyRule` / `weeklyRule` / `windowRule`），原有的 `*Interval` 方法改为在规则上取周期，规则本身只有一处表述。`Gauge` 增加 `rule`（默认 nil，不破坏既有调用点），历史图的重置虚线改由它按各自算法反推。

**一处要紧的分工**：限流窗口的 `windowInterval` 刻意**不外推**。`windowRule` 能按固定时长往回推（历史图要用），但当前窗口仍只认服务端说的那一段——否则过期时会外推出一个包含此刻的新周期，把上一个周期的用量安到新周期头上，比原 bug 更糟。

验收标准逐条：

| 标准 | 用例 |
|---|---|
| 自然日 | `CalendarDailyTests` |
| 非整点购买时间 | 当地 14:35 重置，含「14:35 之前属于前一天」 |
| 固定 24 小时 | `testFixedDurationKeepsItsExactLengthAcrossTheTransition` |
| 日历月 | `SubscriptionAnniversaryTests`（1 月 31 天而非 30；2 月夹到月末） |
| 夏令时 | 春 23 小时 / 秋 25 小时；与固定时长的分道扬镳 |
| 时区变化 | 同一条「当地 0 点」在两个时区是不同瞬间 |
| 周期 ID 稳定 | 同周期内任意时刻 ID 相同；不同规则算出同一起点时 ID 不撞 |
| 未知不产生伪造倒计时 | `UncomputablePeriodTests` |

覆盖测试：新增 `ResetPolicyTests.swift` 29 例（总数 219 → 248 全通过）。

**反向验证**：把日历加法换回秒数加法 → 两例时长断言失败（82800 / 90000 ≠ 86400）；去掉 pace 的窗口守卫 → 三例失败（已用 70% 的过期采样确实算成 `onPace(delta: 0.3)`）。

写测试时有两处**我自己的断言先写错了**，核对后确认是测试错而非代码错，值得记下来：① 夏令时的错位出现在切换日的**次日**（3/8 那段 +86400 秒仍落在切换生效之前，所以还是当地 0 点）；② 31 号的订阅在 2 月 15 日时，2 月 28 日那次**还没到**，所以它正确地落在 1/31–2/28 这个周期里。两处都补了用例把正确行为钉住。

## EXT-005：历史数据与 token 聚合适配

历史存储需要支持连接身份、额度桶、采样时上限和周期信息。建议按数据职责分别保存，不必在每条记录重复完整策略对象。

```text
连接：providerID + endpoint + accountID
额度采样：quotaBucketID + timestamp + used + limit + unit
周期：periodID + periodStart + periodEnd + resetPolicyVersion
用量来源：累计计数 / 周期计数 / 供应商直接历史
覆盖状态：实测区间 / 空档 / 无法归属
```

**额度趋势：** 使用采样时的上限，避免升级订阅后历史百分比被改写。优先按真实周期 ID 或可信规则切段，计数器下降作为补充证据。历史空档和重置保持不同画法，未知边界不画成已知事件。

**Token 图表：** 区分“用量按哪一天汇总”与“订阅何时重置”，二者不必相同。默认可以保留按日用量视图；供应商数据支持时，增加按额度周期查看。每天 14:35 重置的周期应显示完整起止时间，不能仅标为某个自然日。只有当前周期总量时，不将其拆成未经观测的每日用量。

**增量归属：**

- 优先使用供应商直接提供且口径明确的历史或周期统计。
- 只有累计值时，仅将来源一致、单调且落在可确定聚合区间内的差值纳入对应桶。
- 跨日、跨周期、长时间断档或计数器回退时，若无法可靠归属，则不加入具体日期或周期；可记录为未归属数据及其时间范围。
- 不同时累加供应商周期总量和本地差值，避免重复统计。
- 采样及对应聚合更新在同一事务中提交；保底采样和增量基线分别维护。

**验收标准：** 支持不同重置时刻且不跨周期错误连线；历史上限调整不改写旧点；跨边界差值不会被全部塞入后一个桶；缺失与零用量可区分；重启和写入失败不会漏计或重复累计。

**实施记录（本地可做的部分已完成）**

本条多数要求在前几轮已随对应缺陷修掉，这轮补上剩余两块。

验收标准逐条：

| 标准 | 状态 |
|---|---|
| 历史上限调整不改写旧点 | ✅ OPT-008：`Sample.limits` 三态（有上限 / 当时不限 / 不知道），每点用自己那条 |
| 缺失与零用量可区分 | ✅ OPT-004 的 `hasCompleteUsage`；`TokenDelta` 从不补零 |
| 重启和写入失败不会漏计或重复累计 | ✅ OPT-003 的事务 + OPT-002 的两条基线 |
| **不跨周期错误连线** | ✅ 本轮：周期 ID 切段 |
| **跨边界差值不会被全部塞入后一个桶** | ✅ 本轮：未归属增量 |

**一、周期 ID 成为直接证据。** 原先判断「跨没跨重置」只有一条线索：计数器下降。它看不出**静默重置**——整个周期都没用过时，前后用量都是 0，计数器不降，但确实跨了周期。现在按 EXT-004 的 `ResetRule.periodID` 判断，计数器下降降为**补充证据**（管理员手动清零、服务端改配置，规则不知道，只剩它能看出来），两条任一成立即算重置。规则算不出周期时（滑动窗口、未知）自然退回旧证据。

同时把 `connectors` 的 `cycleStart` 闭包换成规则本身——重置边界和「是否跨过重置」从此出自同一处，不会出现「按 A 判断断开、按 B 画边界」的不一致。

**二、跨日界的增量不再硬塞。** 原先 `addTokenDelta(day: DayKey.string(for: sample.at))` 把整段差值记到**后一条采样所在的那天**。23:58 → 00:02 的那段会整个算进新的一天。

新增 `TokenAttributionPolicy`：两次采样落在同一天才归进去，跨了日界就记成 `unattributed(from:to:)`，存进新表 `unattributed_deltas`（schema v3）。**刻意不按时间比例劈开**——用量不是均匀流淌的，很可能全部集中在某一侧，按比例分是编的，只是错得比「整段塞后一天」更隐蔽。总量经 `unattributedTotal` 可查，界面可以如实说明「另有 N tokens 无法归到某一天」。

**补充实施（第二轮）**

重读原文后发现两处我上轮误归到「未包含」、其实纯 Core 可做的缺口：

**一、「无法可靠归属…可记录为未归属数据及其时间范围」只做了一半。** 跨日界的做了，但**长时间断档的增量仍被静默丢弃**：`TokenDelta.between` 内部有个 30 分钟的间隔检查，超了直接返回 nil，那段用量就从总量里彻底消失了。

| | 含义 | 该怎么办 |
|---|---|---|
| 首次安装 / 计数器回退 | **连总量都算不出** | 只能重建基线 |
| 断档过久 / 跨日界 | **算得出，但说不清哪天** | 总量必须留下来 |

于是把「算多少」和「记到哪」拆开：`TokenDelta.between` 只做单调性检查（去掉 `maxGap`），间隔规则移到 `TokenAttributionPolicy`，和日界规则并列——两条任一不满足就归到 `unattributed`。丢掉会让总量凭空变少，那是另一种不诚实。

**二、「未知边界不画成已知事件」没做。** 重置连接段的起点画在「重置发生的那一刻」，而那个时刻可能本身是推算的（日重置时刻还没观测到，先当作本地零点）。原先它和服务端明确给出的边界画得一模一样。

`QuotaConnector` 增加 `isBoundaryInferred`，取值跟着 `TimeWindow.isInferred` 走（即 `ResetProvenance` 的可信度）；图表对推算边界用更淡的描边。和「(估算)」那个标签是同一件事。

**撤回：30 分钟间隔规则（2026-09-24，EXT-010 讨论时）**

上面第二轮把 `TokenDelta.between` 里的 `maxGap` 挪进了归属策略，和日界规则并列。重审后撤掉，只留日界一条。

理由：「app 关了三天」本来就跨日界，日界规则已经兜住（上一段 `testWideGapIsNotAttributedToAnyDay` 在没有间隔规则时照样通过，说的正是这件事）。间隔规则**单独起作用**的只剩「同一天内间隔较长」这一种情况，而那里没有什么可编的：接口给的是累计值，两端都在今天，中间的用量只能发生在今天。不知道的只是今天哪个时段，按天的柱子不问这个。它是从旧 `maxGap` 原样搬过来的，搬的时候没重新问「它在新位置上还防什么」。

**实施记录（范围经用户收窄为「只改菜单栏图标」，已验收）**

本条原文把问题归到「图表」，入口是用户提供的亮色主题实机截图。照文档要求先复现定位、不预先认定是系统反色 —— 定位结果**和原文的归属不一致**，记在这里免得后来者照标题去图表里找：

| 位置 | 亮色主题下的实际表现 | 处置 |
|---|---|---|
| **菜单栏图标** | 中性色解析成**黑色**，而同一条菜单栏上系统自己的文字是白的 | **本轮已改** |
| 面板的额度进度条 | `QuotaStatus.normal` 取 `.primary`，亮色下是纯黑填充 | **用户决定保持现状** |
| 图表本身（网格、坐标文字、空档阴影、柱体） | 截图里**没有**发现难辨认的黑色 | 无需改动 |
| 额度曲线取 `Color.accentColor` | 跟随用户在系统设置里选的强调色，与「彩色元素保持现有语义」相左 | 记录在案，本轮不动 |

**根因不是系统反色，是参照物错了。** 图标的动态颜色按 `NSApplication.shared.effectiveAppearance` 解析，那是 **app 的**外观（跟随亮/暗主题设置）；而亮色主题下菜单栏是深是浅其实由**壁纸**决定 —— 深色壁纸上系统会把自带图标和文字转成白色，app 的外观却照样是「亮色」，于是 `labelColor` 解析成黑色，黑字画在深底上。截图里系统自己的菜单栏文字是白的、我们的图标是黑的，两者并排，这就是直接证据。

改法：外观不再由绘制方自己取，改为**调用方从状态栏所处的环境取、一路传进来**。`MenuBarExtra` 的 label 抽成 `MenuBarLabel` 这个独立 View，在那里读 `@Environment(\.colorScheme)` —— 写在 `App` 结构体里读到的是 app 级环境，等于没改，这一步是本条的关键。

两条**刻意没走**的路，各自的代价：

- **写死中性白/灰**（用户最初的字面要求）。浅色壁纸 + 亮色主题时菜单栏是浅底黑字，写死白色等于把同一个毛病原样翻转过来；点开面板时图标周围那层浅色高亮底同理。跟随明暗在用户当时那张深色壁纸下**结果与写死白色相同**，但换壁纸不会翻车。
- **改用模板图**。系统会按菜单栏实际明暗自动着色，四种组合全对，但整张图变单色，蓝色的剩余时间环和橙/红警示色一起失去 —— 文件头注释当初正是为此否决了它。

1. 将现有 claude-relay-service 实现迁移到适配器，保留原有账户及菜单栏选择的映射。

3. 使用去敏的真实接口样例验证各供应商适配器，覆盖成功、缺字段、异常类型、认证失效、超时和接口变更。
4. 验证账户切换、并发刷新、通知去重和持久化事务，优先解决已有审查清单中的关联问题。
5. 验证 macOS 13 兼容性及更高版本行为，执行核心测试、应用编译、界面交互和主题截图检查。

**验收标准：** 现有用户配置和历史可迁移；原功能无回归；新供应商必须通过真实协议验证后才声明支持；失败时保留明确的错误或过期状态。

**实施记录（四条完成，第 5 条无机器可做）**

本条的大半在 EXT-001/002 做掉了，剩下的是这次补齐的。逐条对账：

**1. 迁移到适配器，保留账户与菜单栏选择的映射 —— 完成。** EXT-002 建接口并迁走中转站实现；菜单栏选择靠「桶 ID 取值等于旧 `QuotaKind` 的 rawValue」零迁移。

**2. 版本化迁移 —— 完成，并修掉一个阶段 3 新引进的风险。**

`user_version` 的 v1→v2、v3→v4 已在 OPT-008 与 EXT-001 阶段 2 落地。这次补的是**分区键的碰撞**：`storageKey` 从前只由 apiId 派生，而 tu-zi 的账户标识是响应里的 `key_id`，一个短整数（`4439` 这种）；自建中转站的 apiId 可以是任意字符串。撞上则两个账户的历史**静默合并**——曲线对不上、token 增量互相污染，而且合了再也分不开。

接入第二家之前这个风险不存在，是阶段 3 带来的。现在 `storageKey = derive([providerID, apiId])`。

老用户的历史靠 `legacyStorageKey` **惰性认领**接上：分区键是 apiId 的 SHA-256，哈希单向，库里只有结果算不回去 —— 映射只有「用户此刻切到哪个账户」那一层才同时知道两个键。所以不是启动时一次迁完，而是切到哪个账户就迁哪个。代价是迁移时机分散，换来的是**没有任何一个账户的历史会被孤立**。

认领有两道闸：新键下一行都没有、旧键下确实有。两个条件合起来使它幂等。**只有兜底适配器的账户能认领** —— 存量配置没有 providerID，一律按兜底算，那个年代的历史只可能属于它；让别家也来认领，认领到的正好是另一家的历史，等于在迁移里把要修的碰撞又犯一遍。

`preferenceKey` 刻意仍不含 providerID：它已带 baseURL，两家的服务地址不可能相同。**只在真会撞的地方加键**，每加一个都要付一次迁移的代价。

**3. 去敏样例覆盖成功 / 缺字段 / 异常类型 / 认证失效 / 超时 / 接口变更 —— 完成。**

前三类原先就有（`ModelTests` + 阶段 3 的 `TuziProviderTests`，后者的 payload 形状照抄真实响应、数值全编）。**认证失效和超时从前一条都测不到** —— 适配器直连 `URLSession.shared`，没有地方插手。

加了 `HTTPTransport` 接缝（生产路径默认仍是 `URLSession.shared`，行为不变），以及测试框架的 `runAsync`（带 5 秒超时——这套框架没有进程隔离，一个永不返回的 await 会挂死整轮测试且看不出是哪条）。新增 12 例覆盖 401、连接失败、超时、200 里夹着服务端错误、返回 HTML、认证头的位置、以及**没有密钥时一个请求都不发**。

最后那条有具体理由：发了的话对方回 401，用户看到「认证失败」就去检查一把其实没问题的 key，而真正的原因是钥匙串里那条不见了（换过机器、重装过系统），需要完全不同的处置。

**这一片抓到一个弱测试**，值得记下来。注入「吞掉传输层的错误、拿空数据继续走」时**全绿**：解码照样会失败，于是照样抛，而我的断言只写了「会抛」。可用户看到的从「连接超时」变成了「无法解析响应」——后者会把他送去检查一个其实没问题的网址。断言改成核对错误本身（`URLError.code`）后才抓住。这是项目记过的「被另一条规则顺带兜住」的又一例。

**4. 账户切换、并发刷新、通知去重、持久化事务 —— 策略层完成，App 层接线未覆盖。**

`InFlightGate` / `RefreshGate`（OPT-001）、`AlertPolicy` 的账户命名空间（OPT-005/006）、`HistoryStore.transaction`（OPT-003）都有测试并做过反向验证。**没覆盖的是 `UsageService.refresh` 里那几处接线** —— 它读 `Config`（UserDefaults）、标了 `@MainActor`，而测试目标只编 Core。要覆盖得把 App 层的配置读取也抽成可注入的，那是比本条大得多的改动，没有做。

## EXT-010：账户存档与快速切换

**由用户提出（2026-09-24），已完成并实机验证，见本条末尾「修复记录」。**

**现状与需求：** 应用只存一个账户，换账户要去对应网站翻出 apiId 或 API Key 重新粘一遍。订阅了多家之后这个来回成本高到没人愿意切。需求是：配置成功且「测试连接」通过之后可以存档该账户，下次从下拉里直接选；存档时可自定义名称，方便记忆和管理。

**这条比它听起来小得多。** 该分账户存的东西已经全都分账户存好了：

| 东西 | 键 | 切走再切回来 |
|---|---|---|
| 历史曲线 | `derive([providerID, apiId])` | 原样还在 |
| 钥匙串里的密钥 | `credential.<fullIdentityKey>` | **还在** —— `Config.apply` 只写不删，全项目没有一处删过 |
| 学到的日重置时刻 | `learnedDailyReset.<preferenceKey>` | 还在 |
| 通知去重命名空间 | `notificationNamespace` | 还在 |

整个应用里唯一是单值的，只有「此刻选中的是哪个」。所以要新长出来的只有：一张列表（`providerID` + `baseURL` + `apiId` + 昵称，存 UserDefaults）、一个下拉、以及一条切换路径。

**已定的设计决定：**

- **仍是单账户切换，不做同时显示两家。** 那条 EXT-001 已明确定过不做。特意在这里重申，是因为有了下拉之后「为什么不能两个一起看」会显得只差一步，而实际上那一步很大：菜单栏只有一个位置放数字，面板布局、历史窗口、通知全都假设只有一个活跃账户。
- **切换不能复用 `Config.apply`。** `apply` 是「配置一个新账户」，它要写钥匙串所以必须拿到密钥；切换到已存档的账户手里没有密钥，**也不该有** —— 只写那三个身份字段，密钥照旧由 `Config.connection(for:)` 去钥匙串取。两件事，两个函数。
- **昵称默认填 `ConnectionReport` 带回的名字**（中转站是账户名，tu-zi 是套餐名），可改。存档的时机本来就是「测试通过」，那份报告里已经有名字了。强制用户从空白填起是给常见路径加摩擦。
- **切换、改名、删除都在设置窗口的存档列表里；面板头部只显示当前账户。**（2026-09-24 实机后改定）原计划把切换做成面板顶上的下拉——切换是高频动作。实现后用户看过实机，决定去掉下拉：面板头部第二行改为「账户名 · Active」（名字优先用存档昵称，没存档用对方报的名字）加刷新按钮（刷新期间旋转）。切换改为存档列表每行一个「切换」按钮，代价是切一次要先打开设置窗口。议过但没选的：点击头部账户名弹出菜单切换、放进面板底部的设置区。
- **删除 = 删列表项 + 删钥匙串条目，历史库留着。** 「删除」的语义是「我不再用这个账户了」，把能花钱的密钥留在钥匙串里不干净；而历史是最有价值也最难重建的东西，且它按身份分区，哪天同一账户重新加回来会自动接上。**必须在确认框里把这两件事都说清楚**，不能默默做。
- **当前账户不许删**（2026-09-24 定）。删了密钥而身份还停在它上面，面板立刻报「缺少密钥」；删完自动切到别的，又是替用户选账户，列表删空时还得另议。设置窗口里那一行的删除按钮灰着，说明「先切到别的账户再删」；`UsageService.forgetArchived` 里有兜底断言。
- **没有新的明文暴露。** 列表里存的是 `providerID` / `baseURL` / `apiId` / 昵称，全都是已经明文存在 UserDefaults 里的东西；密钥仍然只在钥匙串。这点值得写在实现注释里 —— 「保存账户列表」听起来像在存一堆凭据。

**原先「动手前必须先决定的一件事」—— 已解决（2026-09-24）。** 担心的是换账户丢掉 token 基线、跨过切换那段的用量归属打折扣。读代码后结论：

- **基线逻辑本身不用改。** token 一变采样就必落盘（`Sample.differs` 首先比累计值），所以库里最后一条的累计值恒等于内存里最后一次观测。切回来从库里补基线，等价于重启一次 app —— 总量不丢、不重复。
- **真正的折扣来自归属策略里一条 30 分钟间隔规则**：当天切走超过半小时再切回，那段会被打进「未归属」，而界面不展示未归属。该规则已撤掉（见 EXT-005 末尾「撤回」一段）。现在只有跨午夜的那段会进未归属，那是真说不清。
- tu-zi 不报累计 token，本就不受影响。
- 「未归属要不要在界面上显示」是另一件事（EXT-005「未包含」末条），与本条无关，不并进来。

另议过但**否决**的：后台继续刷新已存档的账户以保持基线热着。请求数按账户数翻倍，且违背「只有一个活跃账户」的前提（通知、`InFlightGate` 都建在它上面）—— 那是在绕路做「同时显示多家」。

**还需要考虑的：** 存档项指向的钥匙串条目可能已经不在了（换过机器、重装过系统、用户手动删过）。`Config.connection(for:)` 已经优雅处理（适配器抛「缺少密钥」，而不是发一个没有认证头的请求去换一个误导人的 401），但存档列表上大概该标出来，否则用户只会看到选了之后一直刷不出数。

**已定（2026-09-24）：不预检，选中后刷新失败时再提示。** 预检要在打开设置窗口时逐条读钥匙串，文件版钥匙串首次访问会弹授权框，存档多了会连弹。而失败路径已经基本齐了：`TuziProvider` 抛 `errMissingCredential`（「缺少密钥，请重新填写并测试连接」），`applyAccount` 切换时先清空旧快照，于是面板落到「无数据 + 报错」那一支，显示的就是这句。实现时只补两处：

- 那一支（`PopoverView` 的 `message(stateOfflineTitle, …)`）**没有去设置窗口的按钮**，得去折叠区里找「配置账户」。给它加一个，和未配置状态那个按钮一样。对认证失效等其他错误同样有用。
- 标题 `stateOfflineTitle` 英文是「Can’t reach the server」，对缺少密钥、认证失效都是错的（中文「暂时取不到数据」是中性的）。英文改成中性说法。**不做**按错误类型换标题 —— 那要给 `APIError` 加类型，为一句标题不值。

**修复记录（2026-09-24，实机验证全部通过）**

分四步做，前两步是纯逻辑、后两步是界面，每步停下来给用户看过。提交：`bad2220`（前置：撤掉 30 分钟规则）、`33bf00e`（四步主体）、`3d2d44d`（实机后的界面调整）。

**前置：动手前那件事其实不用改基线。** 详见本条上文「已解决」一段和 EXT-005 末尾的「撤回」。结论是切换等价于一次重启，总量不丢；真正的折扣来自一条同一天内也生效的 30 分钟归属规则，已撤掉，单独提交。

**一、存档列表（Core）。** 新文件 `Sources/Core/AccountArchive.swift`：`ArchivedAccount`（身份 + 昵称）和 `AccountArchive`（按存入顺序，同一身份只一条）。放 Core 是为了能测 —— App 层这套测试框架碰不到。几条要点：

- 判重用**完整身份**，和钥匙串那条的键同口径。同一 apiId 换了网址是两条存档：切换时三个字段都要写回，合成一条就切不回其中一个。
- `save` 挡三种：没配全的、占位身份 `unresolvedAccountID`（和 `Config.apply` 那道门同理）、去空白后为空的昵称。同一身份再存只改昵称、位置不动。
- 从 UserDefaults 解码时**坏条目单独跳过**，不连累整张列表 —— 一条读不出就清空，等于替用户删了所有存档。解码结果也走 `save`，所以占位身份和重复项进不来。

新增 10 例（401 → 411）。**反向验证**四处，各自有用例变红：判重只看 apiId、放行占位身份、一条坏数据清空整表、改名顺手加进未存过的账户。

**二、切换路径（App）。**

- `Config.select`：只写三个身份字段，不碰钥匙串；不在存档里的拒绝。`Config.apply` 末尾那三行抽成私有 `writeIdentity` 两者共用 —— 身份哪天多一个字段，不会只改一处。

- `UsageService.applyAccount` 里「身份变了之后」那段（清快照、通知与历史换账户、`accountGeneration += 1`、重启定时器、立刻刷一次）抽成 `accountDidSwitch`，`selectAccount` 共用（不变量 5）。
- `UsageService.archive` 是 `@Published` 副本、写回 Config，和 `menuBarStyle` 等设置项同一做法；只经 `archiveCurrentAccount` / `renameArchived` / `forgetArchived` 改，**列表只有这一个写入方**。起初让 `Config.forget` 也改列表，成了两处写同一份，已收回。
- `forgetArchived`：先删钥匙串、后删列表项（反过来的话，钥匙串删失败时密钥成了界面上够不着的孤儿）；当前账户拒删，有兜底断言。

**四、设置窗口。**

- 测试通过后状态行下多一行「同时存档，名称：」，默认勾上，昵称预填对方报的名字；已存过的沿用用户起的名字，重测不冲掉。勾着存档而名字为空时保存按钮灰掉。存档发生在 `applyAccount` 成功之后，钥匙串写失败时不留下取不到密钥的存档。

## EXT-011：第三方供应商的接入分类

**由用户提出（2026-09-24），目前只是梳理，未实现。**（原案措辞。现状：已收敛到 Coding Plan 范围，sub2api / claude-code-hub 已接入、输入改为先粘服务地址，见本条末尾。） 目标是把分类配置好，让绝大多数第三方 API 订阅能照着分类直接接进来。**前提：不统一输入方式**（见下文「议过、未采用」）。

**范围：只做第三方。** 官方的两种都不在本条：

- **官方按量付费 API**：有 Usage & Cost Admin API，但要组织级的管理员 key（权限远大于一把普通 key），且只有花费、没有额度和重置周期 —— pace 缺了分母，接进来只是个「本月花了多少」的计数器。
- **官方 Pro / Max 订阅**：5 小时 + 每周额度，模型上和 CodaPace 最契合；但程序可读的用量接口没有公开文档，要借 Claude Code 登录存下的 OAuth token，接口不稳、凭据敏感、条款上有灰色地带。

### 两条分类轴

| 轴 | 两类 | 决定什么 |
|---|---|---|
| **接入方式** | 中转站类 / 服务商类 | 用户要填什么、请求发到哪 |
| **额度形态** | 周期额度 / 总额度（余额） | 能显示什么，有没有速度判断 |

**额度形态这条轴通用层已经处理好了**：适配器报几条额度就显示几条（EXT-001 的额度桶），没有重置周期的额度走 `PaceVerdict.unavailable`，不给判断。要做的只在第一条轴上。

### 接入方式：按「地址由谁提供」划分

| | 中转站类 | 服务商类 |
|---|---|---|
| 本质 | 一套软件，谁都能部署 | 一家公司自己运营的平台 |
| 一个适配器对应 | **一种软件** | **一家公司** |
| 用量接口地址 | **用户提供**（每个部署都不同） | 写死在适配器里 |
| 用户要填 | 地址 + 凭据 | 只要凭据 |
| 现有例子 | claude-relay-service | tu-zi |
| 新增一个的成本 | 一次写好，所有部署都能用 | 每家一次，要改代码发版 |

判据选「地址由谁提供」而不是「自建 / 托管」「开源 / 商业」：claude-relay-service 的用户未必自己搭；开源软件也常被拿去商用。这两对说法的边界都不清楚，地址由谁提供是硬的。

**命名的一个坑**：国内社区通常把 tu-zi 这类平台**也叫中转站**（本质都是转售上游模型）。项目内部按上面的判据用；对外（README）用「服务商」时要一句话定义，免得读者以为 tu-zi 不算中转站。

**另一个事实：很多「服务商」其实是中转站。** 国内大量商业中转站自有域名和品牌，底层是 new-api 换皮（控制台的菜单、「令牌」「额度」等用词和 new-api 一样）。技术上它们归中转站类 —— 接好一个 new-api 适配器可能一次覆盖一大片，比逐家接服务商划算得多。

### 唯一的结构性缺口：输入形态

设置窗口现在**只有一个输入框**，两个现有适配器恰好都只要一样东西：

- claude-relay-service 是特例：用量页面网址里**同时带着地址和 apiId**。
- tu-zi 只要 key，地址写死（`TuziProvider.baseURL`）。

**大多数中转站软件是「地址 + key」**（new-api 即是），一个框装不下。所以支持中转站类的前提是：**适配器声明自己要不要 Base URL，要的话设置窗口多显示一个框。** 除此之外，接入一家就是加一个适配器文件、在 `ProviderRegistry.all` 里加一项 —— EXT-002 的验收标准不变。

**一个已存在的识别冲突**：`TuziProvider.detect` 认任何 `sk-` 开头的 key，new-api 的 key 也是 `sk-`。机制现成：`ProviderRegistry.candidates()` 返回多个时让用户选，`resolve(_:using:)` 有手动指定通道（注释原话「定不下来时应该让用户选，而不是替他猜」）。接上界面即可，不要改成按顺序先到先得。

### 候选名单

**中转站类（按软件）**

| 软件 | 状态 | 用量接口 | 额度形态 | 优先级 |
|---|---|---|---|---|
| claude-relay-service | 已支持 | 统计页，查询参数带 apiId | 周期额度 | — |
| new-api | 待接入 | `GET /api/usage/token`，`Authorization: Bearer sk-…`，**有公开文档** | 令牌总额度（`total_granted` / `total_used` / `total_available`），无重置周期 | **高**：大量商业中转站是它换皮 |
| sub2api | 待核实 | 未找到公开的用量接口 | 未知 | **高**：与 claude-relay-service 同一作者，自称 CRS2，是其后继，现有用户可能迁过去 |
| one-api | 待核实 | 大概率是 OpenAI 风格的 `/v1/dashboard/billing/*` | 总额度 | 低：new-api 由它分出，份额在往 new-api 走 |

**服务商类（按公司）**：tu-zi 已支持；其余**有真实账户时逐家接入**，每家用浏览器开发者工具（Network 面板）看它的用量页面调了哪个接口 —— tu-zi 的 `/reseller/v1/quota` 就是这类地址。

### 已知的坑（接入 new-api 时）

- **额度单位不是美元**，是 new-api 内部的 quota 单位，换算比例各站可配。百分比（已用 ÷ 总额）不涉及单位，可以直接显示；金额只在站点明确声明时显示，否则 `QuotaUnit.unknown` 显示裸数字（不变量 3）。
- **令牌额度 ≠ 账户余额。** 这个接口只返回令牌层面的额度，没有日用额，所以**给不出速度判断**。社区已有 issue（QuantumNous/new-api #3122）在要「用 token 查余额和日用额」。
- **二次开发站点会改字段**（有的返回 `total_usd_*`）。解码走 `Decoding.swift` 的严格路线，字段对不上如实报错，不去猜。
- 上面的接口是 2026-09-24 查文档得来的，**动手前必须拿真实站点核对路径、字段和单位**，和当初核对 tu-zi 的单位同理。没有真账户不要凭文档写。

### 建议的推进顺序

1. 界面支持「地址 + 凭据」：适配器声明是否需要 Base URL。所有中转站类接入的前提。
2. new-api 适配器：有公开文档、覆盖面最大，但要真实站点实测后再写。
3. sub2api：先弄到账户，用开发者工具查接口。
4. 服务商：逐家按需。

**卡在：** 第 2、3 步都要真实账户，用户尚未确认手上有没有。

### 议过、未采用：统一成「Base URL + API Key」

设想是所有供应商都填用户在 Claude Code / CC Switch 里本来就填的那两样，测试连接时按顺序探测归属。用户最终决定不统一。议的过程里理清的几件事，留着备查：

- **能统一的只是输入，取用量的协议统一不了。** 每家路径、认证、响应格式都不同，现有两家的数据一样都不会少，也一样都不会多。
- **服务商类需要「用户填的域名 → 用量接口地址」的映射**，只能人工查出来写进适配器，没有自动发现的办法。tu-zi：用户在 Claude Code 里填的是 `https://api.tu-zi.com/coding`，用量接口在 `coding.tu-zi.com`，同一根域名。
- **域名匹配必须带点号**：「等于 `tu-zi.com` 或以 `.tu-zi.com` 结尾」，不能只写「以 `tu-zi.com` 结尾」，否则 `evil-tu-zi.com` 也会命中，key 被发到别人那里。这条是安全边界。
- **按顺序探测时，专门适配器必须排在通用适配器之前**，否则一家同时支持详细额度和通用余额接口的服务商，会被通用的先认走，日 / 周 / 月数据静默丢失，还不报错。
- claude-relay-service 据称有「用 key 换 apiId」的接口，可以换完只存 apiId、丢掉 key，凭据敏感度仍是只读（未核实）。
- 认出是 tu-zi 但额度接口拒绝（比如一把非 Coding Plan 的 key）时，倾向报错说明，而不是转给通用余额适配器再试 —— 否则同一家有时显示日周月、有时只显示余额，让人困惑。

这几条**在不统一的前提下大多不再需要**；但「专门在前、通用在后」和「域名匹配带点号」两条，将来接 new-api 通用适配器时照样适用。

### 实测：`api.tu-zi.com`（2026-09-28）

用户问 `https://api.tu-zi.com/console` 支不支持。**不支持，而且眼下不值得接。**

- 它是 tu-zi 的**按量付费站**，和已支持的 `coding.tu-zi.com`（Coding Plan）是两套东西。公开的 `/api/status` 是 new-api 的格式，站名「兔子API」。
- 用量接口是 `/api/usage/token/`，**要带结尾斜杠**，不带会 301。
- 单位有据：`/api/status` 公开 `quota_per_unit = 500000`、`display_in_currency = true`、`quota_display_type = USD`。可以按这个换算成美元，不算发明（不变量 3）。
- 信封和文档不一样：成功是 `{"code": true, "data": …, "message": "ok"}`，失败是 `{"success": false, "message": …}`。
- **用户那把令牌是 `unlimited_quota: true`**：`total_granted` 是 500000（$1），`total_used` 远大于它，`total_available` 是负数。不限额的令牌，这三个数里只有「已用」是真的。显示一个负余额就是撒谎。
- 真正在扣的是**账户余额**，只有 `/api/user/self` 给。它不认 `sk-` key，要控制台生成的「系统访问令牌」加 `New-Api-User` 请求头，那把令牌能以用户身份操作整个账户。只为显示一个没有周期、给不出 pace 的余额，不值得让用户交出它。

### 实测：GAC Code（`gaccode.com`，2026-09-28）

用户问 `https://gaccode.com/credits` 属于哪类适配器。**服务商类，自家平台，不是 new-api，也不是 CRS。不接。**

- 整站是一个单页应用，所有路径都返回同一个网页。`/api/status` 是它自家的健康状态，不是 new-api 的格式。
- 积分页调用 `GET /api/credits/balance`，认证用的是**网页登录后存在 `localStorage` 里的 `token`**。
- 额度模型本来很合适：后台有 `creditsCap`（积分上限）和 `refillRate`（每日补充），有周期，可能给得出 pace 判断。另外还有加油包和美元账户。
- **API Key 查不了**：用户拿自己的 key（`sk-ant-oat01-` 开头，故意做成官方 OAuth 令牌的样子，好让 Claude Code 直接用）请求 `/api/credits/balance`，返回 `{"error":"Unauthorized"}`。
- 只剩登录令牌这条路，而它能以用户身份操作整个账户（改密码、建删 key 都走同一个令牌）。和 `api.tu-zi.com` 的 `/api/user/self` 是同一个取舍，同样不接。

**什么时候重新考虑**：它开放了用 API Key 查积分的接口，或者用户愿意接受交出登录令牌。

### 已完成：统一命名 + 粘错时指路（2026-09-28）

用户提出：适配器统一命名；粘了用量网址时告诉用户这是哪家、该粘什么。

- **命名规则**写在 `UsageProviderAdapter.displayName` 的注释里：中转站类用软件名，服务商类用「品牌 + 产品」，不写类别。tu-zi 改名为 **`tu-zi Coding`**，和按量付费站区分开。**`providerID` 没改**，存量配置、历史分区、通知去重都不受影响。
- 适配器新增两项声明：
  - `inputHint`：一句话说该粘什么。
  - `recognizesSite(_:)`：这是不是这家的网站。服务商按主机名全等来认，中转站按路径 `/admin-next` 认。
- 由 `ProviderRegistry.siteOwner(for:)` 统一处理，缺 `https://` 时自动补上。设置窗口里解析不出连接、但认得出网站时，状态行显示「这是 X 的网站。请改粘 …」，**不发任何请求**。
- 「认不出」的文案原来是「请确认它是中转站的用量统计页面」，那是只有一家时的说法。现在改成对照上方支持列表。
- 5 例测试。

**用户实机发现一处指错路（同日修正）：** 起初 tu-zi Coding 认整个 `tu-zi.com`，于是用户粘 `api.tu-zi.com/console`（new-api 的按量付费站）时，被提示「请改粘 API Key」，照做了也连不上。指错路比说「认不出」更糟。

#### 输入改为「先粘服务地址」（用户 2026-09-28 同意）

用户在编程工具（Claude Code、Codex）或 CC Switch 里本来就填过 **Base URL** 和 **key**。先粘地址有三个好处：
1. 厂商靠**域名**就能认出来，多家 key 都以 `sk-` 开头的撞车问题就没了；
2. 国内、国际区也由域名决定（`open.bigmodel.cn` 对 `api.z.ai`），不用另加开关；
3. 认不出的域名就是中转站。

流程：
1. 输入框提示粘服务地址。
2. 认出是哪家、而这家要 key 的，下面出现 key 框。
3. CRS 统计页网址照旧一次完成（网址里带着 apiId）。
4. 认不出的地址当作中转站，也出现 key 框，测试连接时在**用户自己的站点上**分别试 sub2api 和 claude-code-hub 的接口。

这和上文「议过、未采用：统一成 Base URL + API Key」的区别有两处：
- 那次是**固定两个框**，现在是**按需出现第二个框**；
- 那次靠**按顺序发请求去试**是哪家，现在厂商靠**域名直接认出**，不发请求。

当时议出的两条规矩照样适用：域名匹配带点号（或主机名全等）；专门的适配器排在通用的前面。

### 已完成：sub2api 适配器（2026-09-28，本机部署实测）

**实测环境**：`/tmp/codapace-lab/` 里的 sub2api v0.2.9 官方可执行文件，配便携版 PostgreSQL 16.6 和源码编译的 Redis 8.10.2。全部只监听 `127.0.0.1`，没碰任何系统目录；实测内存约 240 MB。

建分组之前，sub2api 要求管理员逐字输入一句合规承诺短语。这一步**经用户明确同意**后才提交，确认记录只存在实验室的本地数据库里。

**三种响应形态**（`GET /v1/usage`，用站点发的 key，`Bearer`）：

| 形态 | 怎么认 | 额度 |
|---|---|---|
| key 自带限额 | `mode: "quota_limited"` | `quota` 总额，加 `rate_limits[]` 的 5h / 1d / 7d |
| 订阅分组 | 有 `subscription` 对象 | 日 / 周 / 月的上限和已用，外加 `weekly_window_start`、`expires_at` |
| 钱包余额 | 只有 `balance` | 没有周期 |

**实测才发现的事**（照文档写一定会错）：
- key 限额的窗口**从第一次使用起算、满时长重置**（09:23 开始的 1d 在次日 09:23 重置），**不是自然日**。所以标题用「5 小时 / 24 小时 / 7 天」，不用「今日」「本周」。
- 窗口没用过时，`window_start` 和 `reset_at` 都是 `null`。
- key 必须挂在某个分组下，否则返回 403「not assigned to any group」。
- 失败响应有两种格式：`{"code":"INVALID_API_KEY","message":…}` 和 Anthropic 风格的 `{"type":"error","error":{"message":…}}`。
- sub2api 的 key 也以 `sk-` 开头，印证了「先粘服务地址」的必要。
- 时间戳带微秒和 `+08:00`，和 tu-zi 的格式一样，**共用 `TuziDate`**，没有另写一份。

**映射与取舍**：
- **身份** = key 的 SHA-256 前 16 位。响应里永远没有账户 ID，哈希本身就是身份，不是占位（和 tu-zi 的「先占位、测过再换真身份」不同）。换 key 就是新账户。
- **key 限额的三个窗口**：`serverProvided`，起止原样用服务端给的。没用过的窗口不给周期，也不拿「现在 + 时长」编一个。
- **总额**只显示，不参与 pace。
- **订阅的日额度**：按服务端时区的自然日 0 点，时区读自时间戳的偏移，标成推算（`inferred`）。
- **订阅的周额度**：服务端给的锚点加 7×24h，来源标成 `configured`（长度来自源码）。
- **订阅的月额度**：响应**没有月窗起点**，只显示用量，不给 pace。
- 某一档上限为 `null` 表示不限，不产出这条额度。
- **钱包余额**测试连接时明确报错「钱包余额模式，没有周期额度」，不显示一个空面板。
- 用户粘的 Base URL 可能带 `/v1` 之类的路径，只保留 scheme + host + port。
- 注册表里**排在最后**（专门的在前、通用的在后）。认任何网址，所以协议新增 `siteMatchIsGuess`，界面上说「未识别的站点，将按 sub2api 测试」，不说「已识别」。

**验证**：
- 13 例测试，样本结构照抄真实响应、数值全编。
- 反向验证 6 处，每处都会变红：日重置标成服务端给的、没用过的窗口编一个起止、不拦钱包模式、只认一种错误格式、不剥 Base URL 的路径、拿 key 本身当身份。
- 另外把核心代码编进一个一次性程序，**对真实的 sub2api 服务**用三把 key 各跑了一次 verify 和 fetchUsage，结果和预期一致。

**刻意没做的**：
- **部署在子路径下的站点**（反代到 `/sub2api/`）会被截掉前缀。代码里有 `ponytail:` 注释，遇到再说。
- **订阅月额度的重置时刻**：推不出来，不猜。

**同日追加（用户同意）：连接报告的「推算」提示改看实际数据。**

原来的提示「接口不提供日重置时刻，将由观测推算」是按能力声明给的：没声明 `.dailyResetTime` 就出现。这句话只对 CRS 成立，对 sub2api 两种模式都不对：key 限额模式的重置时刻是服务端给的，订阅模式是按时区推的，也不靠观测。

- **判定**：改成看这次快照里有没有标成推算的周期（`window.isInferred`）。
- **命名与文案**：finding 改名 `resetInferred`；文案改成「部分额度的重置时刻是推算的，界面上会标注『推算』」，不点名是怎么推的。
- **对 CRS 行为不变**：测试连接时它还没学到日重置，日额度按默认假设推算，照样提示。
- **代价**：CRS 用户少看到「之后会通过观测学到」这层意思。
- **测试**：3 条测试按新判定改写，另加 2 例，sub2api 两种模式各验一次。改回按能力声明判断时，3 条会变红。
- **没做**：`.dailyResetTime` 这项能力声明因此没有任何代码读取了，只剩各适配器里的声明和几条测试。其他几项能力声明也大多是这样，删不删是另一个决定，没有顺手做。
- **claude-code-hub**：之后照同样的方式本机部署实测。届时认不出的网址要依次试两种软件。

### 已完成：claude-code-hub 适配器（2026-09-28，本机部署实测）

**实测环境**：`/tmp/codapace-lab/` 里的 v0.9.6 源码，用 bun 1.3.10 装依赖、`next build` 构建（约 2 分钟，最大进程内存峰值约 2.1 GB），跑 standalone 产物，配便携版 PostgreSQL 和 Redis。全部只监听 `127.0.0.1`。bun 缓存和 Next.js 遥测都关在实验室目录里，`~/.bun` 始终没有生成。实验室磁盘占用约 3 GB。

**和调研结论不一样的地方**（照文档写一定会错）：
- **默认配置下 API Key 查不了额度。** 会话令牌模式默认 `opaque`，`/api/v1/me/quota` 只认登录会话。调研依据的官方文档说「直接用 `X-Api-Key` 调用」，在默认配置下不成立。解法：拿 key 调 `POST /api/auth/login`，从 `Set-Cookie: auth-token=sid_…` 里取出会话令牌（7 天有效），放进 Bearer 头去查。这和它网页端「用 API Key 登录」是同一条路，权限不超过那把 key。
- **响应里一个时间戳都没有**，读不出服务端时区。时区另查 `/api/v1/system/timezone`，带会话能拿到 `{"timeZone":"Asia/Shanghai"}`，是服务端明说的。
- **`dailyResetMode` / `dailyResetTime` 是 key 的**，不是账户的：默认 key 显示 `fixed 00:00`，而用户那层设的是 04:00。账户层的日重置规则，以及两层的 5 小时重置方式，响应里都没有。

**认证流程**（用户 2026-09-28 同意，并选定会话存钥匙串）：
- 依次试：存着的会话 → key 本身（兼容 legacy / dual 模式的站点）→ 用 key 登录换新会话。只有 401 才往下走一步。
- **会话必须复用**：每登录一次，站点就多一条登录记录、Redis 里多一个会话。
- 会话存在 `SessionTokens.store`（名字里刻意不带供应商，App 不必认识是哪家要会话，不变量 6），App 启动时换成钥匙串实现（`KeychainSessionTokenStore`，键是 `session.` 加完整身份），重启 app 也能接着用。
- 删除存档账户时，会话连同 key 一起删（`Config.removeCredential`）。
- 登录请求关掉了 cookie 处理，否则 URLSession 会把令牌存进 app 的 cookie 文件，成为一份没人管的、能用 7 天的凭据。
- 这个过程用户完全看不到，不会打开浏览器。

**映射**：
- key 级、账户级各有 5 小时 / 日 / 周 / 月 / 总额，**只显示设了上限的**。标题带层级前缀，用 `BucketTitle.scoped`，显示成「Key · 本周」「账户 · 本月」。
- 周、月：服务端时区的周一 0 点、每月 1 号 0 点（源码 `time-utils.ts` 确认）。来源标成 `configured`，给 pace。
- key 的日额度：固定时刻的，用服务端给的时刻和时区，来源 `server`；滚动的，标题写「24 小时」，不给周期。
- 账户的日额度、两层的 5 小时、总额：只显示用量。
- **查不到时区就哪条都不给周期**，不拿本机时区顶上。
- 身份用 key 的哈希，和 sub2api 共用 `AccountIdentity.hashedKeyID`；站点根也共用 `ProviderRegistry.siteRoot`。
- 没有累计 token 和请求数，`totalCost` 等都传 nil。

**陌生网址的尝试顺序**：先 claude-code-hub，再 sub2api（`ProviderRegistry.guesses`）。设置窗口依次测试，**保存的是真正跑通的那个连接**（`verifiedConnection`）；都失败时，把每一种的原因都列出来。
- 实测发现：先试 sub2api 的话，它的 `GET /v1/usage` 在 claude-code-hub 站点上会被**当成一次模型转发请求**（返回「No available providers」并开了一个会话），真实站点上等于借用户的 key 往上游多发一个请求。所以 claude-code-hub 排在前。
- **剩余情况**：key 本身无效时，claude-code-hub 失败后仍会试 sub2api，那一个请求会进它的转发路径。只发生在测试连接、并且 key 无效时，上游也会直接拒绝，没有再处理。

**验证**：
- 14 例测试。另加 1 例锁定尝试顺序。
- 反向验证 7 处，每处都会变红：不复用会话、登录后不存会话、让 URLSession 存 cookie、查不到时区就用本机的、账户日额度套用 key 的规则、滚动当成固定、只认 problem+json 的错误。
- 一次性程序对**真实服务**用三把 key（只有账户级限额 / key 固定日重置 04:00 / key 滚动）走完整的「依次尝试 → verify → 第二次 fetch」。三把都由 claude-code-hub 验证通过，第二次刷新复用了会话，周、月、日的边界都和预期一致。

**刻意没做的**：
- **子路径部署**：同 sub2api，截掉前缀。
- **5 小时和账户日额度的重置规则**：响应里没有，不猜。
- **累计 token 和请求数**：接口不给。
- **钥匙串授权框**：会话令牌是新条目，每次重新构建后读它会多弹一次（ad-hoc 签名的已知局限，见 project-notes「钥匙串可用」）。

图表主题定位可以提前独立进行；tooltip 和周期展示应与新的数据口径协调，避免后续重复实现。

## 已确定方向与待明确细节

已确定采用：供应商 API 优先、共享额度按实际计费桶统计、独立产品或模型额度由供应商声明、无法归属用量不强行分摊、macOS 13 自定义 tooltip，以及显式图表中性色主题。（原案。其中 tooltip 渲染与显式中性色后来经用户决定不做，见 EXT-006 / EXT-007 / EXT-008。）

实施前仍需明确首批目标供应商、真实链接格式、认证方式和响应样例。“Codex API 订阅”优先按供应商提供的 API 服务需求理解；若还需支持官方客户端订阅额度，应单独验证其获取方式和授权范围，不能假设与 API 计费接口相同。

本文未指定任何尚未验证的供应商接口，也未承诺对任意管理后台自动抓取。完成单项后，记录验证结果，再勾选对应任务。
